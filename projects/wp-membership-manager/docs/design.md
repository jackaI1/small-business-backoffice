# Storage and operational boundaries

The plugin has one per-site table, `<prefix>wpmm_records`, with an InnoDB engine and a unique `(kind, record_key)` index. Record kinds are member, renewal, event, registration, sponsor, campaign and delivery. Payloads are JSON; SQL values are prepared, and dashboard values are escaped. The `Store` interface separates WordPress persistence from the domain rules tested by PHPUnit. Activation creates the schema, and a version check supports later schema upgrades. Deactivation preserves data; deleting the plugin also preserves records for explicit backup and removal by the administrator.

Membership edits, receipts, registrations, sponsorship changes and imports acquire a per-site database advisory lock and use transactions. Lock acquisition is nonblocking so another writer gets a retry error instead of interleaving changes. The database must support `GET_LOCK`, transactions and InnoDB. Renewals extend the later of today or the member's existing expiry by one calendar year; PHP's calendar arithmetic takes February 29 to March 1 in a non-leap year. Receipt IDs cannot be reused for a different member or amount.

A draft snapshots consenting recipients and their addresses. A delivery is skipped if consent or the address changes before send. A send action holds the writer lock and handles at most 100 messages. Unlike imports, sending does not open a database transaction: `sending` is committed before SMTP and `sent` or `failed` afterwards. Rolling back a database transaction cannot unsend an email. A crash, lost database connection or SMTP timeout can leave uncertain acceptance; no software can guarantee exactly-once delivery across separate mail and database systems. `sending` is never automatically retried, while an explicitly failed SMTP call can be retried by the administrator. Reconcile uncertain deliveries with the provider before any database repair, and take a backup first. This is a small-association, manual-batch design, not a background bulk-mail queue.

The open and unsubscribe links contain 256-bit random bearer tokens, separate for each delivery, with no email address in the URL. Public open requests return a one-pixel image; only sent deliveries can count as opened, once each. Unsubscribe GET requests show a confirmation form, so link scanners do not opt recipients out just by following a URL. The POST must echo the secret token. Unsubscribe responses use no-cache and no-referrer headers. Treat exported email bodies and these URLs as sensitive because their tokens authorize opting out.

`manage_options` protects all admin reads and writes; WordPress nonces protect all mutations. HTML is filtered with `wp_kses_post` when a draft is submitted or previewed. Names are escaped during email personalization. The only public routes are tracking and unsubscribe. The Mailpit transport is enabled only with `WPMM_DEMO_SMTP=1`; other sites retain their configured `wp_mail` transport. The demo binds WordPress and Mailpit web ports to loopback, and does not publish database or SMTP ports. Do not expose its published example credentials to the internet.

Reports are all-time snapshots. Renewal totals sum the receipt ledger. Sponsorship totals sum the latest stored agreements. Open totals count distinct deliveries, not people, and are approximate. The plugin does not infer campaign-attributed renewals. The table is intentionally straightforward for a small association: most reports and token lookups scan a record kind in PHP, and there is no pagination or retention scheduler. At larger scale I would add indexed typed tables, pagination, background delivery, token hashes, retention controls and provider bounce handling.

## Local verification and cleanup

`demo/setup.sh` installs WordPress, activates the plugin and seeds an empty association. Running it again preserves existing records. `tests/integration.php` creates its own temporary table and drops it in a `finally` block. `tests/http_smoke.py` changes only the synthetic demo records and checks the actual Mailpit inbox. Run it once on a fresh demo. CI always runs `docker compose down -v --remove-orphans`, including failure paths.

A manual demo stays running for inspection until `docker compose down` is called. `-v` also removes the demo database and WordPress volume; back up anything wanted first. The setup does not start or restart a Docker engine, kill other processes, or open browser tabs. A failed local setup may leave its own containers available for diagnosis; use the same cleanup command when finished.

## Card payments

Stripe Checkout is used in test mode; see [card payments](payments.md) for the state machine, webhook events, refunds and failure handling. Three decisions matter most. The plugin never sees card numbers. A place or renewal changes only after a signature-verified webhook. Renewals reuse the receipt ledger with a payment-derived receipt ID, so replays cannot extend a membership twice. The HTTP client is injected, which keeps the runtime free of a Composer dependency and lets tests check real request bodies and real signatures without network access.
